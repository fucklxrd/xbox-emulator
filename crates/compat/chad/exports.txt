1 XDspActivate stub | type 1 convolution (XDefiant) runs on the host with the console validation; types 2 (FFT) and 3 (IFFT) pass the console descriptor checks and then return E_NOTIMPL: their DSP microcode and buffer layout are not in any dump (see docs/BLOCKERS.md, chad FFT/IFFT streams)
2 XDspConnect implemented
3 XDspConnectWithMaximumStreamLimit implemented | console 0x2bc0: E_INVALIDARG for mem/size/activations, streams > 0x100 or priority > 2, then E_POINTER for a null out; XDspConnect is this call with 0x100 streams, priority 2 (console 0x2b90); limits kept per client, the CPU convolution has no hardware stream queue to apply them to
4 XDspDeactivate implemented
5 XDspDisconnect implemented
6 XDspSubmitCommand implemented
7 XDspSubmitCommandWithEnvelope implemented | console 0x3200 -> 0x2524 (shared with XDspSubmitCommand 0x31e0, envelope NULL): for convolution streams the envelope is taken at the first command of every 8 (counter +0x150 & 7) and must lie in the XDspConnect memory (APU translation 0x1888 fails -> E_INVALIDARG); later commands in the group reuse a snapshot and a NULL envelope at a group start disables it. The DSP microcode that applies it is not in any dump, so the gain math is inferred from the GDK description (per-block gains applied during convolution, left then right): IR partition k is scaled by gain[k], right gains at roundup4(partitions). Known gaps vs console: the console snapshot holds only 0x20 bytes per channel and takes the right half at envelope+[+0x148]*4, and +0x148 is not confirmed to equal the partition count
